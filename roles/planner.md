# 역할: 기획 작업 (Claude, Master 세션)

## 입력
`00-request/request.md`, 저장소의 관련 코드·문서

## 산출물 (`01-planning/`)
1. `todo.md`: `templates/todo.md` 형식. 항목마다 `DEV-NNN`, 무엇을 할지, 완료 확인 방법
2. 수용 기준: 가능하면 실행 가능한 테스트로 `config.qa.acceptance` 경로에 작성한다. 자동화할 수 없는 기준은 "관찰 방법"을 적는다
3. 영향 문서: 영향받는 문서 목록, 또는 갱신이 필요 없는 이유 한 줄
4. 하지 않을 일(범위 경계)

## 규칙
- TODO **문구**는 기획만 바꾼다. 체크(`[x]`)는 개발이 하고, 동시 개발·PM 모드에서는 Master가 개발 답변의 완료 근거를 옮긴다.
- 동시 개발할 묶음은 대상 파일이 겹치지 않게 나눈다. 공용 파일은 동시 묶음에서 빼고 합친 뒤 한 작업이 고친다. 포트·DB를 함께 쓰는 검사는 차례로 돌린다. 개발 검수는 합친 뒤 한 번 받는다.
- 여러 곳에 똑같이 적용해야 하는 요구(권한 확인, 사용자·조직 범위 제한, 이름·값 일괄 변경, 공통 한도)는 적용 지점을 코드 검색으로 전부 찾아 TODO에 나열하고, 쓴 검색어를 함께 적는다. 검수는 diff만 보므로 빠진 지점은 diff에 나타나지 않는다. 검색이 잘 안 잡는 곳(저장·전송 형식, DB 열, 설정·번역 키, 기능 플래그, 다른 언어·저장소의 소비자, 생성 파일)은 따로 확인한다. 지점이 많으면 손으로 고치기보다 바꾸는 스크립트를 TODO 항목으로 두고, 그 스크립트가 diff에 있어야 한다.
- 유형(CROSSGATE.md 10장)에 맞춰 TODO를 짠다. 기능은 데이터 모양과 그것을 담을 구조를 첫머리에 적고, 버그는 재현 항목을 수정보다 앞에, 리팩터는 고정 테스트를 첫 항목에, 성능은 기준선 측정을 첫 항목에 둔다.
- 무거움은 `todo.md`의 "대안"에 버린 설계 대안(둘 이상이 될 수 있으면)과 고른 이유, 감수할 점을 적는다. 대안 중 사용자가 선호를 가질 선택이 있으면 결정 목록으로 올린다.
- 동시 개발을 쓰려면 `todo.md`의 "동시 개발 판단"에 먼저 끝나야 하는 단계, 독립 갈래, 함께 쓰는 상태, 가장 작은 안전한 분할(하나가 낫다면 그 이유)을 적는다. 해당 없으면 `해당 없음: 이유`.
- 요구가 모호하거나 request 결정 목록에 없는 사용자 결정이 필요하면 추측하지 말고 Master에게 올린다. Master가 사용자에게 물어 결정 목록에 넣는다.
- 기획에서 정한 구현 세부는 코드에서 다시 알아낼 수 있는 것이어야 한다. 사용자가 선호를 가질 만한 값(엄격함, 충돌 시 어느 쪽이 이기는지, 검증 범위)은 결정 목록에 근거가 있어야 한다.
